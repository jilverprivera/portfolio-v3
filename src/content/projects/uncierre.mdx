<SummarySection title="Summary">

UnCierre is the platform behind Conversion's real-estate operation. It handles the whole path of a property deal: inventory of projects, towers and units, sales quotes, reservations with down-payment installments, customers, rentals with their own installments, payments, receipts and the notifications around them.

It is a work project, not a personal one: it was built at Conversion for a client. The repository is a monorepo with a commercial dashboard, a set of backend services, shared packages and a customer mobile app for rental payments.

The platform unlocked new revenue streams through its quote and booking engines, and sales grew by 40%. Standardizing test-driven development also shortened production release cycles by 30%.

The core of the sales side is an event-sourced reservation service. Instead of overwriting state, every change is stored as an event and projected into the tables the rest of the system reads.

</SummarySection>

<ChallengeSection title="Challenge & strategy">

### Challenge

Selling and renting property involves long, money-heavy processes. A reservation can last months, with installments, discounts and changes along the way, and a system that only stores the current state makes it hard to answer what changed, when and by whom. The commercial team needed to quote and sell faster, with discounts, bonuses, extras, several sellers and installments, and rentals needed their own installments, extensions, contract endings and payments aware of the exchange rate.

There was also a legacy to deal with. The platform had to replace an earlier one whose data model dates from 2020, so the work included carrying that legacy forward while breaking the monolith into services that could change at their own pace. Around the deals, people needed to be kept informed by email, WhatsApp and webhooks, and customers needed a mobile way to pay and to report on their rentals.

### Strategy

The platform was designed around the history of each deal. The core of the sales side became an event-sourced reservation service: every reservation and customer change is stored as an event that can be replayed and audited, then projected into the tables the rest of the system reads. Writes follow business rules through CQRS, while the dashboard reads shaped projections through GraphQL served by Hasura, at the cost of two models to maintain.

Business rules were kept independent from frameworks, databases and messaging through a strict hexagonal architecture. RabbitMQ carries events between services so that notifications and inventory react without blocking a sale, and the event store, projections and rentals live in separate databases so they can evolve independently. Each service ships on its own on Docker Swarm with automatic rollback, a simple option with fewer tools than a larger orchestrator. Test-driven development was standardized across the services.

</ChallengeSection>

<ImplementationSection title="Implementation & final design">

### Architecture

The repository is a monorepo with yarn workspaces and Turborepo: the dashboard, services for reservations, rentals, inventory, notifications and PDFs, Hasura, and shared packages for domain types, a design system, the quoters, a table and the tower view. The reservation service uses event sourcing and CQRS. Commands arrive at an actions endpoint and are handled by command handlers (24 for reservations and 9 for customers). Events are written to an event store, a handler updates a projection database, and post-actions run side effects and publish to the message bus.

Reads go through GraphQL, with Hasura serving the projection and rental databases to the dashboard through 86 tracked tables. The services follow a strict hexagonal architecture, keeping the domain independent from the outside world, with application logic around it and adapters for repositories, messaging and HTTP at the edge. The event store, the projections, the rental data and the core data are separate Postgres databases.

### Messaging

RabbitMQ carries events between services through a durable topic exchange. The notifications and inventory services consume them, and scheduled jobs expire optioned quotes and update rates.

### Clients

The dashboard is built in Next.js with Redux Toolkit, Zustand, Apollo Client with subscriptions, form libraries and a money library for amounts. The mobile app is built in Expo and React Native with file-based routing, for rental payments and reports.

### Quality and delivery

TDD was standardized across the services, with about 20 active Jest files and 7 Playwright end-to-end specs for the main flows: quotes, reservations, rentals, payments, login and inventory. Together with the rest of the work, this shortened production release cycles by 30%. For delivery, seven GitHub Actions workflows build a Docker image per service on a tag, push it to a registry and update a Docker Swarm service with automatic rollback on failure, with secrets managed outside the repository. On the data side there are 89 Knex migrations for the reservation and rental services, plus the legacy Hasura migrations.

### Decisions

Each decision below was taken for a concrete reason and carried a cost, which the table records next to it.

| Decision | Why | Trade-off |
|---|---|---|
| Hexagonal architecture | Business rules stay independent from frameworks, databases and messaging, so each can change without touching the domain. | More structure up front, with ports and adapters to write. |
| Event sourcing for reservations and customers | Deals are long-lived and audit matters, so every change is kept as an event. | More moving parts: an event store, projections and handlers to keep in sync. |
| CQRS with GraphQL reads | Writes follow business rules, and the dashboard reads shaped projections. | Two models to maintain. |
| RabbitMQ between services | Notifications and inventory react to events without blocking a sale. | Operating a broker and designing routing keys. |
| Hasura for reads | A GraphQL API over the projections with little code. | Metadata and migrations to manage. |
| Separate databases per concern | The event store, projections and rentals evolve independently. | Cross-database consistency has to be designed. |
| Docker Swarm with rollback | A simple way to ship each service on its own. | Fewer tools than a larger orchestrator. |
