<SummarySection title="Summary">

Mottika is a multi-tenant transactional ecosystem for a financial-services company. It connects merchants and employee funds with card processors and card-management systems, and it governs how every transaction is validated, routed and processed. It also enables what happens after: pricing, reconciliation, disbursement and cash collection.

It is a work project, not a personal one: it is being built at Tres Astronautas for a client. Mottika is the technical half of a two-part product. This half is everything behind the scenes, and Emisys, documented as its own project, is the visual layer and the channel of communication with the funds.

It is designed with PCI-DSS and ISO 27001 in mind, so that the platform can be certified.

</SummarySection>

<ChallengeSection title="Challenge & strategy">

### Challenge

The story starts with a simple observation: operating cards at scale means connecting many parties that each speak a different dialect. Processors, card-management systems, acquirers and accounting all have their own way of talking, and each connection built as custom code was slow to change and hard to audit.

That left a platform where adding a route or a business rule meant writing code and releasing it, where cash handling at the counter was hard to trace, and where onboarding a new client threatened to mean building yet another system.

### Strategy

The planning work started from an impact map that tied business goals to the people and systems that use the platform. The answer it pointed to was a single, configurable switch placed in the middle. Rules decide where a transaction goes and how it is priced, and the same platform carries it through to reconciliation and cash collection, with each client isolated from the others.

Several goals shaped that proposal. Routing and business rules would be configured, not coded and released, so that traffic could be spread across several processors without deployments. Transactions would be processed securely, fast and exactly once, with idempotency and resilience when a third party was slow or down. Financial integrity would be kept from end to end, from pricing to reconciliation and disbursement, and cash-desk operations would be digitized so that cash handling became auditable. Everything would be governed in one place, with security and a trace of each operation, on a multi-tenant platform where a new client does not mean a new system.

The main technical choices followed from those goals. API-first and contract-first design kept every integration away from the database. RabbitMQ was chosen over Kafka because the workload is task queues with retries, not a log to replay. A schema per tenant with row-level security gave strong isolation, the outbox pattern tied each state change to its event, and a separate tokenizer kept sensitive card data in the smallest possible scope. Pricing was kept from ever blocking an authorization, and accounting was left outside Mottika so that each product owns one job.

</ChallengeSection>

<FeaturesSection title="Features">

| Area | What it enables |
|---|---|

| Transversal services | Users and roles, API keys with scope and expiry, notifications across channels, an immutable audit log, threat detection, analytics and customer-service ticketing. |

### How a transaction flows

Mottika sits between a card processor or a merchant's point of sale and the card-management systems that own the balance and the financial decision. The switch never decides the money: it authenticates, identifies, applies rules, routes and records.

1. **Entry.** Requests arrive through an edge gateway as signed messages with an idempotency key. Other protocols, such as ISO 8583, end in their own gateways.
2. **Card protection.** A dedicated gateway is the only component that ever sees a card number. It tokenizes the card, and everything downstream works on tokens.
3. **Identity and route.** The token resolves to a company, a project and a tenant, and the company's routing rule gives the destination. Unknown tokens and suspended tenants are rejected.
4. **Rules and quota.** Compiled business rules run in order, and the first rejection stops the flow. The fund's quota is checked and reserved.
5. **Transform and journal.** The request is forwarded as is or mapped to the target's format, and the transaction is written to a journal before the outbound call.
6. **One synchronous call.** A single call goes to the target system, with bounded retries and a circuit breaker per destination. A failed or unsigned response becomes a technical decline and releases the quota. It is never an approval.
7. **The asynchronous tail.** The result is stored together with an outbox record, and a worker delivers signed callbacks, domain events and notifications with retries and a dead-letter queue.
8. **Downstream.** Billing, reconciliation, disbursement and the accounting hand-off happen afterwards and never slow the authorization.

<ImplementationSection title="Implementation & final design">

### Architecture

The system is built as event-driven microservices in one Go workspace: seven services and four shared libraries, in 11 modules, with three autonomous areas on top of a shared transversal layer. Those areas are the switch, pricing and point of sale.

A language-neutral contract layer sits apart from the code, holding OpenAPI specs, event schemas and gRPC definitions. Synchronous services use gRPC between them and REST towards clients, and pricing and rule compilation run as queue workers. The transversal concerns, such as roles, audit, key management and observability, are a library linked in-process, so the hot path has no extra network hop. A separate tokenizer is the only component in PCI scope, which keeps that scope small. On the front end, the web apps live in a Turborepo: a merchant self-service panel and an admin panel, with a UI package and an SDK generated from the control-plane contract.

### Domain model

The domain is split into eleven bounded contexts, each owned by one service and connected to the others only through identifiers, APIs and events. The core ideas:

- **Client (tenant)** is the unit of isolation: a merchant, a fund or an integrating platform.
- **Project and company.** A client has projects, projects group companies, and companies own cards. Each card belongs to exactly one company.
- **Configuration** is made of routing rules, transformation profiles, business rules and quotas, published to the switch as a versioned, immutable snapshot.
- **Transaction** records the tenant, the rule and transformation versions applied, the destination, the idempotency key, a trace identifier and the outcome.
- **Point of sale and cash.** Registers, terminals, shifts, sales, corrections, cash closings and collection deliveries.
- **Billing and settlement.** Tariff sheets with adjusters, charges per transaction, period invoices, reconciliation runs and disbursements.
- **Operations.** Audit entries, incidents, dead-letter messages and support cases.

Some invariants hold everywhere: the tenant always comes from the credential and never from a request parameter, another tenant's resource looks like it does not exist, a request is processed once per idempotency key, and amounts are integers in minor units, never floats. A sale only exists inside an open shift, and one without a verdict in time is marked failed and never flips to approved on its own.

### Data and messaging

Data lives in PostgreSQL, with a schema per tenant and row-level security, typed queries and versioned migrations. Messaging runs on RabbitMQ with quorum queues, a retry ladder, dead-letter queues and the outbox pattern, so a state change and its event are committed together. Redis serves the token and rule caches, and audit records go to append-only storage so they cannot be rewritten.

### Edge, identity and security

At the edge, an API gateway keeps separate channels for machine-to-machine traffic, PCI traffic and the portals, and a dedicated gateway handles ISO 8583 messages. Identity relies on OpenID Connect with the tenant carried as a claim. Requests between systems are signed, mutual TLS is used where cards are involved, rate limits are layered and secrets are kept outside the repository.

### Quality attributes

Eight quality attributes were defined, each with measurable acceptance criteria. Latency is handled by keeping everything on the authorization path in memory with a single network call: configuration is preloaded and hot-reloaded, slow operations return "accepted" and finish later, and billing runs after the response. For scalability, instances are stateless behind a balancer, queues absorb backlog, and limits per credential and per fund keep one tenant's spike from hurting the others.

Availability comes from a transactional zone that keeps running when the admin zone is down, failures detected by heartbeat, deploys with no downtime and infrastructure that can be rebuilt from code. Resilience means transient errors are retried with backoff and definitive ones are not, each destination has a timeout and a circuit breaker, and nothing is dropped silently. Security and isolation rest on zero trust between every hop, a second factor for every person, a minimal card-data perimeter, and tenant isolation in layers: the credential, scoped queries and row-level security, with isolation tests running on every pull request.

Auditability relies on two append-only records, an audit log of who did what and a journal of what happened to each transaction, correlated by a trace identifier, so any critical transaction can be reconstructed. Interoperability comes from versioned, contract-first APIs with an owner, linted in CI, with invalid messages rejected at the edge. Finally, maintainability and observability are supported by architecture rules enforced in CI, structured logs, metrics and traces, and a monitoring dashboard for transactions, latency, breakers and quotas.

### UX design

The blueprint defines two web consoles. The admin console is for the platform team, working across tenants on desktop. The merchant console is strictly one tenant and serves four personas: the merchant admin, the cashier, the supervisor and the collection receiver. The cashier screens are tablet-first, with one task per screen.

The key journeys cover onboarding a client and enabling its admin, configuring routing, rules and quotas published as a versioned snapshot, and setting up tariffs and assigning them to a client. They also include making a sale and seeing the verdict, with the receipt and invoice arriving afterwards, closing a shift with a dual validation by cashier and supervisor, and delivering collection and approving reconciliation.

The principles behind them are a single design system, a permanently visible tenant, four kinds of message (success, business rejection, technical failure and "pending") and confirmation with impact before irreversible actions. Offline mode is read-only, and no card data is ever displayed or captured.

### Delivery

The plan spans twenty weeks in seven chunks, from a transversal foundation, through the switch core, integrations, pricing and settlement, observability and support, to point-of-sale operation and cash collection. Each module has its own CI with formatting, vetting, linting and race-detector tests, plus contract linting, secret scanning, static analysis and vulnerability scans, and there is a deploy workflow per service.

Quality is risk-based and starts at definition, not at the end. The deepest testing goes to the switch and its payment seam, integrations, point of sale and billing. Third-party dependencies are treated as a quality risk, and a release-readiness review looks at coverage, defects, regressions, risks and evidence. An architecture decision trail of ten written decisions records why choices were made, and an external architecture partner reviews the work at fixed checkpoints.

### Decisions

The main choices are summarized below, each with the reason behind it and what it costs.

| Decision | Why | Trade-off |
|---|---|---|
| API-first and contract-first | No interface or integration touches the database directly. | Contracts must be written before building. |
| RabbitMQ instead of Kafka | The workload is task queues with retries, not a log to replay. | Audit lives in its own store instead of the broker. |
| Schema per tenant plus row-level security | Strong isolation between clients. | More work to manage migrations across schemas. |
| Outbox pattern | A state change and its event are committed in the same transaction. | Events are delivered at least once, so receivers must be idempotent. |
| A separate tokenizer | Keeps sensitive card data in the smallest possible scope. | One more service to deploy and secure. |
| Pricing never blocks authorization | A missing tariff must not fail a payment. | Pricing runs on a best-effort basis alongside the transaction. |
| Accounting stays outside Mottika | Each product owns one job and hands over a clean boundary. | An integration to maintain between the two. |
| Lean, self-managed data tier | A cost-driven choice for the early stages. | Revised so that no control promised to the client was dropped. |

Some choices, such as the API gateway and the identity provider, were changed after feedback from the client. The written decision trail made those changes cheap to explain and to apply.

<ResultsSection title="Results">

Today the client has the foundation of the platform in place: the control plane and the merchant administration are built, so the operation can be set up and governed per client, each isolated from the others. The part that moves the money, the switch core, pricing, point of sale and the tokenizer, is designed and scheduled for later chunks.

This means there are no production traffic figures, latency results or certification to report yet. Several dependencies on third parties, such as processor sandboxes, the reconciliation file format and an e-signature provider, are still to be confirmed.
