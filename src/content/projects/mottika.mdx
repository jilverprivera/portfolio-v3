<SummarySection title="Summary">

Mottika is a multi-tenant transactional ecosystem for a financial-services company. It connects merchants and employee funds with card processors and card-management systems, and it governs how every transaction is validated, routed and processed. It also enables what happens after: pricing, reconciliation, disbursement and cash collection.

It is a work project, not a personal one: it is being built at Tres Astronautas for a client. Mottika is the technical half of a two-part product. This half is everything behind the scenes, and Emisys, documented as its own project, is the visual layer and the channel of communication with the funds.

It is designed with PCI-DSS and ISO 27001 in mind, so that the platform can be certified.

</SummarySection>

<ObjectivesSection title="Goals">

The planning work started from an impact map that ties business goals to the people and systems that use the platform. The goals are:

- **Route across several processors without deployments.** Routing and business rules are configured, not coded and released.
- **Process transactions securely, fast and exactly once,** with idempotency and resilience when a third party is slow or down.
- **Keep financial integrity from end to end,** from pricing to reconciliation and disbursement.
- **Digitize cash-desk operations** so that cash handling is auditable.
- **Govern everything in one place,** with security and a trace of each operation.
- **Scale as a multi-tenant platform,** where onboarding a new client does not mean building a new system.

</ObjectivesSection>

<FeaturesSection title="Features">

### How a transaction flows

Mottika sits between a card processor or a merchant's point of sale and the card-management systems that own the balance and the financial decision. The switch never decides the money: it authenticates, identifies, applies rules, routes and records.

1. **Entry.** Requests arrive through an edge gateway as signed messages with an idempotency key. Other protocols, such as ISO 8583, end in their own gateways.
2. **Card protection.** A dedicated gateway is the only component that ever sees a card number. It tokenizes the card, and everything downstream works on tokens.
3. **Identity and route.** The token resolves to a company, a project and a tenant, and the company's routing rule gives the destination. Unknown tokens and suspended tenants are rejected.
4. **Rules and quota.** Compiled business rules run in order, and the first rejection stops the flow. The fund's quota is checked and reserved.
5. **Transform and journal.** The request is forwarded as is or mapped to the target's format, and the transaction is written to a journal before the outbound call.
6. **One synchronous call.** A single call goes to the target system, with bounded retries and a circuit breaker per destination. A failed or unsigned response becomes a technical decline and releases the quota. It is never an approval.
7. **The asynchronous tail.** The result is stored together with an outbox record, and a worker delivers signed callbacks, domain events and notifications with retries and a dead-letter queue.
8. **Downstream.** Billing, reconciliation, disbursement and the accounting hand-off happen afterwards and never slow the authorization.

<MotivationSection title="Why the product was built">

Operating cards at scale means connecting many parties that each speak a different dialect: processors, card-management systems, acquirers and accounting. Each connection built as custom code is slow to change and hard to audit.

Mottika puts a single, configurable switch in the middle. Rules decide where a transaction goes and how it is priced, and the same platform carries it through to reconciliation and cash collection, with each client isolated from the others.

</MotivationSection>

<ImplementationSection title="How it was built">

### Architecture

- **Event-driven microservices in one Go workspace.** Seven services and four shared libraries, in 11 modules, with three autonomous areas on top of a shared transversal layer: the switch, pricing and point of sale.
- **A language-neutral contract layer.** OpenAPI specs, event schemas and gRPC definitions live apart from the code. Synchronous services use gRPC between them and REST towards clients, and pricing and rule compilation run as queue workers.
- **A transversal layer linked in-process.** Common concerns such as roles, audit, key management and observability are a library, so the hot path has no extra network hop.
- **A separate tokenizer** is the only component in PCI scope, which keeps that scope small.
- **Web apps** in a Turborepo: a merchant self-service panel and an admin panel, with a UI package and an SDK generated from the control-plane contract.

### Domain model

The domain is split into eleven bounded contexts, each owned by one service and connected to the others only through identifiers, APIs and events. The core ideas:

- **Client (tenant)** is the unit of isolation: a merchant, a fund or an integrating platform.
- **Project and company.** A client has projects, projects group companies, and companies own cards. Each card belongs to exactly one company.
- **Configuration** is made of routing rules, transformation profiles, business rules and quotas, published to the switch as a versioned, immutable snapshot.
- **Transaction** records the tenant, the rule and transformation versions applied, the destination, the idempotency key, a trace identifier and the outcome.
- **Point of sale and cash.** Registers, terminals, shifts, sales, corrections, cash closings and collection deliveries.
- **Billing and settlement.** Tariff sheets with adjusters, charges per transaction, period invoices, reconciliation runs and disbursements.
- **Operations.** Audit entries, incidents, dead-letter messages and support cases.

Some invariants hold everywhere: the tenant always comes from the credential and never from a request parameter, another tenant's resource looks like it does not exist, a request is processed once per idempotency key, and amounts are integers in minor units, never floats. A sale only exists inside an open shift, and one without a verdict in time is marked failed and never flips to approved on its own.

### Data and messaging

- **PostgreSQL with a schema per tenant and row-level security,** with typed queries and versioned migrations.
- **RabbitMQ with quorum queues,** a retry ladder, dead-letter queues and the outbox pattern, so a state change and its event are committed together.
- **Redis** for token and rule caches.
- **Append-only audit storage** so records cannot be rewritten.

### Edge, identity and security

- **An API gateway** with separate channels for machine-to-machine traffic, PCI traffic and the portals, and a dedicated gateway for ISO 8583 messages.
- **OpenID Connect** for identity, with the tenant carried as a claim, signed requests between systems, mutual TLS where cards are involved, layered rate limits and secrets kept outside the repository.

### Quality attributes

Eight quality attributes were defined, each with measurable acceptance criteria. How the main ones are met:

- **Latency.** Everything on the authorization path runs in memory with a single network call. Configuration is preloaded and hot-reloaded, slow operations return "accepted" and finish later, and billing runs after the response.
- **Scalability.** Stateless instances behind a balancer, queues to absorb backlog, and limits per credential and per fund so one tenant's spike does not hurt the others.
- **Availability.** The transactional zone keeps running when the admin zone is down, failures are detected by heartbeat, deploys have no downtime and the infrastructure can be rebuilt from code.
- **Resilience.** Transient errors are retried with backoff and definitive ones are not. Each destination has a timeout and a circuit breaker, and nothing is dropped silently.
- **Security and isolation.** Zero trust between every hop, a second factor for every person, a minimal card-data perimeter, and tenant isolation in layers: the credential, scoped queries and row-level security. Isolation tests run on every pull request.
- **Auditability.** Two append-only records, an audit log of who did what and a journal of what happened to each transaction, correlated by a trace identifier. Any critical transaction can be reconstructed.
- **Interoperability.** Versioned, contract-first APIs with an owner, linted in CI, and invalid messages rejected at the edge.
- **Maintainability and observability.** Architecture rules enforced in CI, structured logs, metrics and traces, and a monitoring dashboard for transactions, latency, breakers and quotas.

### UX design

The blueprint defines two web consoles. The admin console is for the platform team, working across tenants on desktop. The merchant console is strictly one tenant and serves four personas: the merchant admin, the cashier, the supervisor and the collection receiver. The cashier screens are tablet-first, with one task per screen.

The key journeys are:

- Onboarding a client and enabling its admin.
- Configuring routing, rules and quotas, published as a versioned snapshot.
- Setting up tariffs and assigning them to a client.
- Making a sale and seeing the verdict, with the receipt and invoice arriving afterwards.
- Closing a shift with a dual validation by cashier and supervisor.
- Delivering collection and approving reconciliation.

Its principles are a single design system, a permanently visible tenant, four kinds of message (success, business rejection, technical failure and "pending") and confirmation with impact before irreversible actions. Offline mode is read-only, and no card data is ever displayed or captured.

### Delivery

- **Twenty weeks in seven chunks,** from a transversal foundation, through the switch core, integrations, pricing and settlement, observability and support, to point-of-sale operation and cash collection.
- **CI per module** with formatting, vetting, linting and race-detector tests, plus contract linting, secret scanning, static analysis and vulnerability scans, and a deploy workflow per service.
- **Quality strategy.** QA is risk-based and starts at definition, not at the end. The deepest testing goes to the switch and its payment seam, integrations, point of sale and billing. Third-party dependencies are treated as a quality risk, and a release-readiness review looks at coverage, defects, regressions, risks and evidence.
- **An architecture decision trail.** Ten written decisions record why choices were made, and an external architecture partner reviews the work at fixed checkpoints.

<DecisionsSection title="Why it was done this way">

| Decision | Why | Trade-off |
|---|---|---|
| API-first and contract-first | No interface or integration touches the database directly. | Contracts must be written before building. |
| RabbitMQ instead of Kafka | The workload is task queues with retries, not a log to replay. | Audit lives in its own store instead of the broker. |
| Schema per tenant plus row-level security | Strong isolation between clients. | More work to manage migrations across schemas. |
| Outbox pattern | A state change and its event are committed in the same transaction. | Events are delivered at least once, so receivers must be idempotent. |
| A separate tokenizer | Keeps sensitive card data in the smallest possible scope. | One more service to deploy and secure. |
| Pricing never blocks authorization | A missing tariff must not fail a payment. | Pricing runs on a best-effort basis alongside the transaction. |
| Accounting stays outside Mottika | Each product owns one job and hands over a clean boundary. | An integration to maintain between the two. |
| Lean, self-managed data tier | A cost-driven choice for the early stages. | Revised so that no control promised to the client was dropped. |

Some choices, such as the API gateway and the identity provider, were changed after feedback from the client. The written decision trail made those changes cheap to explain and to apply.

</DecisionsSection>

<LimitationsSection title="Limitations and open items">

- **Work in progress.** The design runs ahead of the code: the first chunk is built, while later chunks, such as the switch core and point of sale, are mostly documented.
- **No production claims.** There are no production traffic figures, latency results or certification to report yet.
- **Tests are concentrated** in the control plane, and some services do not have tests yet.
- **Third-party dependencies** such as processor sandboxes, the reconciliation file format and an e-signature provider are still to be confirmed.
- **Early-stage infrastructure** runs in a single availability zone, with more resilience planned for later stages.

</LimitationsSection>
