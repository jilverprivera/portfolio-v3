<SummarySection title="Summary">

GetSellers is a marketplace for US real-estate investor leads. Homeowners who want to sell enter through marketing campaigns, their data is registered as leads, and each lead is routed automatically to the investors subscribed to that county, which the product calls a market.

This is a work project, not a personal one: it was built at Tres Astronautas for a client. The engagement was a handover and modernization of a live product, covering an investor web app, an internal admin site and the API behind both.

Investors sign up, pick markets, add a payment method and receive leads by in-app notification, email or SMS. From there they manage each lead in a pipeline (New Lead, Following Up, Under Contract, Closed, Cold) and can request a refund on a bad lead.

</SummarySection>

<ChallengeSection title="Challenge & strategy">

### Challenge

The work began as a handover of a live product. A marketplace that routes homeowner leads to investors was already running, and the outgoing team had left a technical document behind. Taking it over safely meant not touching anything until its state was understood. The first sprint, called Sprint 0, was spent reviewing that document, running a gap analysis and measuring a performance baseline of the live product, and it named the critical areas: the lead feed, counties, billing and the setup wizard.

The pains were of two kinds. The backend followed a layered structure that made each use case hard to test on its own. And lead delivery was exposed to billing problems, while operations had no tools of their own for refunds, broadcasts, reports, source prices or referrals. On top of that, lead data carried sensitive and duplicate information that should not reach the frontend.

### Strategy

The plan was organized in sprints 0 to 6. After the Sprint 0 review, Sprint 1 restructured the backend and set up the monorepo, and later sprints migrated payments, built the admin site and reworked the product language. The backend moved from layered to hexagonal so that each use case could be tested alone and with less coupling, a large restructure up front in exchange for an extensive unit test suite.

Billing was reworked so that it would never block a lead. A prepaid wallet with auto-recharge, a monthly budget cap and a backup payment method let delivery continue when the primary charge fails, at the cost of more billing states to model and test. Payments moved from Braintree to Stripe so that the wallet and the investor app shared one provider. Lead data was protected by removing sensitive and duplicate data from the schemas and masking personal information in the API before a lead reaches the frontend.

Operations got their own admin site, built from scratch, because the planned refund integration with the client's own backend could not be completed due to connectivity issues. Lead intake relied on webhook adapters that normalize each source's payload, and releases became tag-driven and per app, so the API, the investor app and the admin site can ship independently.

</ChallengeSection>

### Architecture

The repository is a monorepo with yarn workspaces and Turborepo, holding the API, the investor app, the admin site and shared packages for ESLint, TypeScript configuration and a logger. The backend is hexagonal. A request goes from routes to controllers, then handlers, then use cases with one operation each. The domain holds repository interfaces, types, validators and schemas, while infrastructure holds the repository implementations and services such as Stripe, the Mongo connection and Socket.IO. Dependencies are wired by hand in one file, with path aliases per layer, and the tests swap that file for a mock. Socket.IO and the scheduled jobs run inside the same process as the API. There are about 180 routes under /api. C4 diagrams from level 1 to 3, sequence diagrams and a list of API routes live next to the code, along with one feature document per area. ### Lead intake and assignment

Leads arrive at a public webhook, or an admin creates them by hand. One adapter, webhook-lead.adapter, maps the payload: it accepts several names for the same field and normalizes occupancy, motivation and time frame. It is one adapter for one webhook, not one per source. The create-lead use case then finds the market from the city or the zip, adds Batch Data, the source price and a Street View image, and marks the lead as rejected if a required field is missing. A lead with no TCPA consent or no matching market gets a 400 and an entry in the lead log. Leads from one vendor, Hesel Media, are stored and reported to the admins without being assigned.

Assignment tries the county first, then the state, then the nationwide market. Inside a scope the subscribers are sorted by the oldest last assignment, and the lead goes to one investor, not to all of them. Each candidate must stay under the monthly budget and have enough balance. If the balance is short, that subscription becomes placed, the admins are notified and the next subscriber is tried. If nobody qualifies, the admins get an alert. When a lead is assigned, the wallet is debited and the investor gets an in-app notification, an email and an SMS, the last two only if their alert settings allow it. A referral commission is recorded when the investor was referred, and the outbound webhooks for leads and transactions are dispatched.

</DiagramRow>

### Security and data

The API runs Helmet, CORS, a content-type check, a payload size limit, input sanitization and ObjectId validation, and it has five rate limiters: general, auth, create, read and admin. The CORS code can enforce an allow-list of origins, but unless CORS_ALLOW_ANY_ORIGIN is set to false it accepts any origin, so the allow-list is a setting and not the default. Lead personal data is masked in the public feed: last name, email, phone, address and IP address. The endpoints for assigned leads return the full data. Terms and conditions are accepted with a signature and rendered to PDF with Puppeteer. The PDF and the signature are stored under a private S3 prefix and read through signed URLs, while the lead and refund images use public prefixes.

### Payments and scheduled work

Payments moved from Braintree to Stripe in Sprint 3. The braintree package and a few migration scripts are still in the backend. Each investor has one billing document with the balance, the monthly budget, the amount spent this month and the auto-recharge settings. Adding a second payment method gives a one-time 3% discount on the next lead.

Auto-recharge is an event pipeline. When an assignment leaves the balance under the reload threshold, the use case writes pending events, one for each reload amount needed. A cron job every two minutes charges them with a Stripe PaymentIntent, using an idempotency key per event and card, and it tries the investor's other saved cards when one is declined. If all of them fail, the event is marked failed and the investor gets an email. Stripe webhooks for attached and detached payment methods and for succeeded, failed and expired charges keep the local records in line.

Four node-cron jobs run in the API: cleaning expired one-time codes every day at 00:00, processing auto-recharge events every two minutes, processing pending referral commissions every day at 06:00 New York time, and resetting the monthly billing on the first day of the month.

### Life cycles

An investor can set any status on a lead they own, and two of them also change the lead category. A refund starts in progress, an admin completes or rejects it, and either side can cancel it. Completing it credits the wallet with a refund transaction and unassigns the lead. A rejected refund can be requested again with the form prefilled, and only one refund can be open per lead.

### Quality and delivery

The backend has 289 test files (270 unit and 19 integration) written with Jest, supertest and an in-memory MongoDB, with a 60% global coverage threshold on branches, functions, lines and statements. Cron jobs, sockets, utilities, configuration and validators are left out of that measure. The investor app has 55 test files with Vitest and Testing Library. The admin site has Vitest configured but no test files.

Deployments are tag-driven with Azure Pipelines. A tag is a prefix, a semver and an environment, such as b2.0.0-dev. The prefix picks the pipeline: b for the API, f for the investor app and af for the admin site. The suffix picks the repository, bucket and secrets. The API pipeline builds a Docker image, pushes it to ECR and restarts the container on a VM over SSH. The two web apps are built with Vite using variables from AWS Secrets Manager, synced to S3, and the CloudFront cache is invalidated. The pipelines do not run the test suites. The deployment document lists only the test and dev environments, but the pipelines also accept -prod.

### Decisions

Each decision below was taken for a concrete reason and carried a cost, which the table records next to it.

| Decision | Why | Trade-off |
|---|---|---|
| Layered to hexagonal backend | Each use case can be tested alone and with less coupling. | A large restructure up front, in exchange for the extensive unit test suite. |
| Braintree to Stripe | One payment provider for the wallet and the investor app. | The braintree package and some migration scripts remain in the repository. |
| Prepaid wallet with auto-recharge | A lead is paid from the balance at the moment of assignment, and the wallet is refilled later with retries on the other saved cards. | More billing states to model and test, and an investor with no funds is skipped until the wallet is recharged. |
| Round robin inside each market | Leads are exclusive, and taking turns spreads them among the subscribers. | A lead can end up unassigned when nobody has funds. |
| A new admin site built from scratch | The planned refund integration with the client's own backend could not be completed because of connectivity issues. | More surface to build and maintain. |
| One adapter for the lead webhook | Sources name fields differently, so the adapter maps the aliases and normalizes the values before the lead is stored. | A source with a new shape means extending the adapter. |
| Masking lead data in the API | Personal data should not leave the backend unless the investor needs it. | Extra mapping on every lead response. |
| Tag-driven, per-app deployments | The API, investor app and admin site can ship independently. | Releases depend on tagging discipline. |

<ResultsSection title="Results">

The client kept a live product and gained a modernized one. Investors can sign up, pick their markets, add a payment method and receive leads by in-app notification, email or SMS, then work each lead through the pipeline, from New Lead to Closed, and request a refund on a bad lead. The internal team handles refunds, broadcasts, reports, source prices and referrals from the admin site.

The refund integration with the client's own backend was never completed, so that part still has to be closed. No revenue or conversion figures are reported for this engagement.
