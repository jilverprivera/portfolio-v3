<SummarySection title="Summary">

Telemetrix receives device readings over HTTP, WebSocket and MQTT, stores them as time series, shows them in real-time charts and dashboards, and lets you react to them with rules, outbound actions, scheduled tasks, device commands and sandboxed analysis.

Data is organized in channels: a channel groups up to eight data fields, plus location and status. It is a product of its own, designed from scratch for makers and for teams that integrate it into their own systems.

</SummarySection>

<ObjectivesSection title="Goals">

- **Simple device onboarding.** A device only needs an API key and its identifiers to start sending readings over HTTP, MQTT or WebSocket.
- **Ingestion that does not depend on the database.** A reading is acknowledged to the device once it is persisted in the event buffer, not in the time-series database. The design target is a p99 acknowledgement of 50 ms or less.
- **Real time.** A reading must show up on the dashboard within 2 seconds (p95) of reaching ingestion.
- **Secure by default.** Channels are private when created, API keys are stored only as an HMAC, TLS is a production requirement, and every resource is strictly isolated by owner.
- **A sustainable free plan.** The platform was planned for a mix in which about 80% of devices are on the Free plan, so limits are enforced at the edge, before any costly resource is used.
- **Designed for 100,000 active devices in the first year** (a planning assumption), with 250,000 simultaneous MQTT connections as headroom.

</ObjectivesSection>

<MotivationSection title="Why the product was built">

The starting point was a gap between hobby-grade tools and industrial platforms. Makers and small teams need to collect device data, see it live and react to it, without assembling and operating a stack of brokers, databases and dashboards.

The documentation also sets a concrete business model: a SaaS with a massive free plan for makers, and paying customers who integrate the platform into their own systems. That explains several design decisions, above all the low marginal cost of each free device.

</MotivationSection>

<ImplementationSection title="How it was built">

### Architecture

- **Monorepo** with pnpm and Turborepo: the Go API, the Next.js web app, the Expo mobile app, and shared packages for the generated API client, UI components, design tokens, authentication, real time and fonts.
- **Backend as a modular monolith.** A single binary with domain modules (`ingest`, `telemetry`, `rules`, `actions`, `scheduling`, `realtime`, among others) organized as vertical slices with hexagonal architecture. A module never imports another: they communicate through events. Dependency rules are verified with go-arch-lint.
- **Read/write separation (logical CQRS).** Commands write to the transactional model with an outbox; queries read from `read_*` projections and a Redis cache.
- **Decoupled ingestion.** The flow is: validate, apply the plan's rate limit, deduplicate by `message_id`, assign a per-channel sequence number, publish to Redis Streams and reply 202 only after the stream confirms. The telemetry module then persists the data and publishes an event that feeds real time.
- **Event bus and buffer on Redis Streams.** Telemetry is partitioned across 32 streams by channel hash (to keep per-channel ordering), plus streams for domain events, actions and a dead-letter queue.
- **Partitioned Postgres telemetry** by day with `pg_partman`, and per-minute, hourly and daily aggregate tables consolidated by `pg_cron`.
- **MQTT with EMQX.** The broker stores no credentials: it delegates authentication and ACLs to the API through protected HTTP hooks. The API also has a bridge that translates MQTT messages into the same use cases HTTP uses.
- **Real time.** A WebSocket hub in the API for the web and mobile apps, with MQTT as an optional path.
- **Contracts first.** OpenAPI 3.1 and AsyncAPI 3.0 contracts live in `contracts/` and generate the TypeScript client used by web and mobile.

### Authentication and devices

- **Supabase Auth** with global `owner` and `developer` roles, no organizations. Every resource belongs to its `owner_id` and queries are filtered with RLS.
- **One API key per account** (`tpk_` with 256 random bits). Only its HMAC with a server-side pepper is stored, and the full value is shown only once.
- **A device authenticates with three headers:** the API key, the developer identifier and the device identifier. Any failure returns the same 401 so it never reveals which of the three values failed.

### Load and performance

- Configurable Postgres pool (25 connections per replica), with per-query time limits.
- Ingestion caches channel information and the owner's limits for 10 seconds, with generation-based invalidation.
- The telemetry consumer writes in batches of up to 200 readings or 50 ms, using `INSERT ... ON CONFLICT DO NOTHING`, and sends to a dead-letter queue after several retries.
- The last 48 readings of each channel live in a Redis sorted set, so recent-history queries never touch Postgres.

<DecisionsSection title="Why it was done this way">

| Decision | Why | What changed from the 1.0 plan |
|---|---|---|
| Modular monolith instead of separate services | The team is small, and splitting by domain multiplies operations and distributed consistency with no benefit. Separation was kept only where the load profile differs, and those cases live as modules of the same process. | From seven services by load profile (ADR-002) to a modular monolith (ADR-021). |
| Supabase Postgres instead of RDS | A managed service reduces database operations. | Replaces RDS (ADR-018). |
| Partitioned Postgres without TimescaleDB | Supabase stopped offering the extension on Postgres 17. | The roughly tenfold columnar compression is lost. At nominal load, raw volume goes from about 1.3 TB to about 13 TB per month (ADR-019). |
| Supabase Auth instead of Keycloak | Avoids running our own identity provider, and it is already integrated with the database. | Replaces Keycloak (ADR-020). |
| Redis Streams instead of NATS JetStream | Redis was already in the stack for caching, so it avoids another piece of infrastructure. | Replaces NATS (ADR-022). Lower durability and buffer capacity than replicated JetStream. |
| Global roles without organizations | Per-owner resource isolation is enough for the real use case and simplifies permissions and billing. | Removes the multi-organization model of version 1.0 (ADR-023). |
| API key per account with HMAC, no Argon2 | With 256 bits of entropy a slow hash is unnecessary, and it would weigh on the hot ingestion path. | New decision for devices (ADR-025). |
| MQTT for the apps too | The product must support all three transports end to end. Commands still go through the API to validate, audit and deliver. | Exception to ADR-012, which gave MQTT only to devices (ADR-025). |
| Batched writes and read cache | The bottleneck was Postgres, with many dashboard readers and many devices writing. | New load decision (ADR-029). |

Two things were documented as evolution, not as mistakes. Version 1.0 mentions Go 1.23, Next.js 15 and Expo SDK 52, while the current README states Go 1.26, Next.js 16 and Expo SDK 57. ADR-024 (a one-time code per device) was replaced: sign-in is password only.

</DecisionsSection>

<LimitationsSection title="Limitations and open items">

- **WebSocket presence per replica.** With several replicas, knowing which devices are connected is not global. MQTT presence is.
- **Production TLS pending** on the broker and on the WebSocket listeners (`wss`).
- **Redis buffer shorter than planned.** The 24-hour no-loss target does not fit in memory at planning load; the real buffer depends on the instance size.
- **Retention and rollups** of telemetry are still to be completed.
- **No load test against a real Postgres.** Batches were tested with mocks and with a `PREPARE` against the schema.
- **Shared spaces cannot send values to devices.** Commands and real-time readings belong only to the device owner, until it is defined how to authorize someone else without the commands module reading the spaces module.
- **Low-level auditing.** A LOW event accepted into the queue can be lost if the process dies without shutting down cleanly.
- **References without a document.** ADR-026 and ADR-027 are cited in ADR-028 but are not in the repository.

</LimitationsSection>
