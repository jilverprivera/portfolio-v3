<SummarySection title="Summary">

Telemetrix receives device readings over HTTP, WebSocket and MQTT, stores them as time series, shows them in real-time charts and dashboards, and lets you react to them with rules, outbound actions, scheduled tasks, device commands and sandboxed analysis.

Data is organized in channels: a channel groups up to eight data fields, plus location and status. It is a product of its own, designed from scratch for makers and for teams that integrate it into their own systems.

</SummarySection>

<ChallengeSection title="Challenge & strategy">

### Challenge

It began with a gap. On one side are hobby-grade tools, fine for a weekend prototype; on the other, industrial platforms built for companies with a team to run them. Makers and small teams sit in between: they need to collect data from their devices, watch it live and react to it, but they do not want to assemble and operate a stack of brokers, databases and dashboards just to get there.

The business model made the problem harder. Telemetrix was planned as a SaaS with a massive free plan for makers, and paying customers who integrate the platform into their own systems. With roughly 80% of devices expected on the Free plan, every free device had to cost almost nothing to serve, so the design could not afford waste on the hot path.

### Strategy

The plan started from the device. A device should only need an API key and its identifiers to begin sending readings, whether over HTTP, MQTT or WebSocket. From there, the most important choice was to keep ingestion independent of the database: a reading is acknowledged once it is safely in the event buffer, not when it lands in the time-series store, with a design target of a p99 acknowledgement of 50 ms or less. A reading then has to reach the dashboard within 2 seconds (p95), so people see what their devices are doing as it happens.

Cost and safety shaped the rest. Plan limits are enforced at the edge, before any expensive resource is touched, which keeps the free plan sustainable. Channels are private when created, API keys are stored only as an HMAC, TLS is a production requirement and every resource is isolated by its owner. All of this was sized for 100,000 active devices in the first year, a planning assumption, with room for 250,000 simultaneous MQTT connections.

<ImplementationSection title="Implementation & final design">

### Architecture

Everything lives in one monorepo managed with pnpm and Turborepo: the Go API, the Next.js web app, the Expo mobile app, and shared packages for the generated API client, UI components, design tokens, authentication, real time and fonts. The contracts come first: OpenAPI 3.1 and AsyncAPI 3.0 files in `contracts/` generate the TypeScript client that web and mobile both use.

The backend is a modular monolith, a single binary with domain modules such as `ingest`, `telemetry`, `rules`, `actions`, `scheduling` and `realtime`. Each one is a vertical slice with hexagonal architecture, and a module never imports another: they talk through events, with the dependency rules verified by go-arch-lint. Inside, reads and writes are separated (a logical CQRS): commands write to the transactional model with an outbox, while queries read from `read_*` projections and a Redis cache.

The life of a reading shows how the pieces fit. It is validated, checked against the plan's rate limit, deduplicated by `message_id` and given a per-channel sequence number. Then it is published to Redis Streams, and only when the stream confirms does the API reply 202. The telemetry module persists it afterwards and publishes an event that feeds real time. Redis Streams is both the event bus and the buffer: telemetry is spread across 32 streams by channel hash to keep per-channel ordering, with more streams for domain events, actions and a dead-letter queue.

In storage, telemetry sits in Postgres partitioned by day with `pg_partman`, and per-minute, hourly and daily aggregates are consolidated by `pg_cron`. For devices that speak MQTT, EMQX stores no credentials at all: it delegates authentication and ACLs to the API through protected HTTP hooks, and a bridge in the API translates MQTT messages into the same use cases HTTP uses. The web and mobile apps get real time from a WebSocket hub in the API, with MQTT as an optional path.

### Authentication and devices

Sign-in uses Supabase Auth with two global roles, `owner` and `developer`, and no organizations. Every resource belongs to its `owner_id`, and queries are filtered with row-level security.

A device proves who it is with an API key, a developer identifier and a device identifier. Each account has one key (`tpk_` with 256 random bits), and only its HMAC with a server-side pepper is stored; the full value is shown once. If any of the three values fails, the answer is the same 401, so it never reveals which one was wrong.

### Load and performance

The bottleneck turned out to be Postgres, with many devices writing and many dashboards reading, so the load work went there. The pool is configurable (25 connections per replica) with per-query time limits. Ingestion caches channel information and the owner's limits for 10 seconds, with generation-based invalidation. The telemetry consumer writes in batches of up to 200 readings or 50 ms using `INSERT ... ON CONFLICT DO NOTHING`, and sends a reading to the dead-letter queue after several retries. Finally, the last 48 readings of each channel live in a Redis sorted set, so recent-history queries never touch Postgres.

### Decisions

| Decision | Why | What changed from the 1.0 plan |
|---|---|---|
| Modular monolith instead of separate services | The team is small, and splitting by domain multiplies operations and distributed consistency with no benefit. Separation was kept only where the load profile differs, and those cases live as modules of the same process. | From seven services by load profile (ADR-002) to a modular monolith (ADR-021). |
| Supabase Postgres instead of RDS | A managed service reduces database operations. | Replaces RDS (ADR-018). |
| Partitioned Postgres without TimescaleDB | Supabase stopped offering the extension on Postgres 17. | The roughly tenfold columnar compression is lost. At nominal load, raw volume goes from about 1.3 TB to about 13 TB per month (ADR-019). |
| Supabase Auth instead of Keycloak | Avoids running our own identity provider, and it is already integrated with the database. | Replaces Keycloak (ADR-020). |
| Redis Streams instead of NATS JetStream | Redis was already in the stack for caching, so it avoids another piece of infrastructure. | Replaces NATS (ADR-022). Lower durability and buffer capacity than replicated JetStream. |
| Global roles without organizations | Per-owner resource isolation is enough for the real use case and simplifies permissions and billing. | Removes the multi-organization model of version 1.0 (ADR-023). |
| API key per account with HMAC, no Argon2 | With 256 bits of entropy a slow hash is unnecessary, and it would weigh on the hot ingestion path. | New decision for devices (ADR-025). |
| MQTT for the apps too | The product must support all three transports end to end. Commands still go through the API to validate, audit and deliver. | Exception to ADR-012, which gave MQTT only to devices (ADR-025). |
| Batched writes and read cache | The bottleneck was Postgres, with many dashboard readers and many devices writing. | New load decision (ADR-029). |

Two things were documented as evolution, not as mistakes. Version 1.0 mentions Go 1.23, Next.js 15 and Expo SDK 52, while the current README states Go 1.26, Next.js 16 and Expo SDK 57. ADR-024 (a one-time code per device) was replaced: sign-in is password only.

<ResultsSection title="Results">

For a maker or a small team, the result is a platform that already covers the path from device to decision. Devices send readings over HTTP, MQTT or WebSocket and see them on live dashboards, and people can react to them with rules, outbound actions, scheduled tasks, device commands and sandboxed analysis, through a web console and a mobile app. A reading is designed to reach the dashboard within 2 seconds.

The product is still in development, and not every one of the 85 features in the backlog is verified as complete. Some pieces still to come are production TLS, finishing telemetry retention, and letting shared spaces send values to devices. The performance targets are design goals, not measured results.

</ResultsSection>
