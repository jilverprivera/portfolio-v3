<SummarySection title="Summary">

NIDO is a condominium management platform. A resident gets notices from the administration, authorizes visitors, reserves common areas, signs up for events, chats with neighbors, pays fees, buys from local providers and uses partner benefits.

It is a work project, not a personal one: it was built at Tres Astronautas for a client. The platform has an API, a web portal, a resident mobile app and a staff app, in Spanish and English with light and dark themes.

There are six roles: resident, guard, condominium admin, platform admin, partner and provider. Residents use the mobile app, guards use the staff app (or the web portal when their condominium allows it), and every other role works from the web portal.

</SummarySection>

<ChallengeSection title="Challenge & strategy">

### Challenge

Life in a condominium ran through a lot of separate channels: group chats, paper notices, guard logbooks, receipts sent as screenshots and word of mouth for local services. Residents, administrators and guards each lost time to it, and local providers and partners had no clear way to reach the people living there.

### Strategy

The proposal was to bring those flows into one product, with the right tool for each role. That meant one app for daily life in a condominium, from notices and visitors to fees and local commerce, with a resident-only mobile app and a web portal for administration, guards, partners and providers. Many condominiums would share one platform, with data scoped to each of them.

Two principles shaped the design. Conversations had to be private, so chat messages are encrypted individually, with keys managed outside the database. And every sensitive action had to be traceable, so each mutating flow writes an audit record. Receipt-based payments came first, so fees could be collected right away while the payment gateway is integrated gradually.

</ChallengeSection>

<ImplementationSection title="Implementation & final design">

<DiagramRow item={{ src: "/diagrams/nido/architecture.svg", title: "Architecture", caption: "Clients, the API on Cloud Run with its REST and Socket.IO sides, the data stores and keys, and the outbound services.", width: 1200, height: 680 }}>

### Architecture

The repository is a monorepo with yarn workspaces and Turborepo: the API, the web portal, the resident app, the staff app and two shared packages, one for contracts and one for a profanity filter. The API has 37 modules. Each one is hexagonal, with a domain layer free of frameworks, an application layer with handlers, use cases and services, and an infrastructure layer with controllers and repositories. Dependencies only point inwards, and the rules are written down for people and for AI agents. Click a diagram to open it at full size.

Data lives in two databases. PostgreSQL through Prisma holds the relational data, and MongoDB holds chat conversations, messages and read state. A Socket.IO gateway for chat runs in the same service as the REST API. The Next.js web portal is exported as static files, uses a locale segment in its routes and is served from Firebase Hosting. Both mobile apps are Expo apps built with EAS.

</DiagramRow>

<DiagramRow item={{ src: "/diagrams/nido/chat-security.svg", title: "Chat encryption and the WebSocket fix", caption: "A data key per conversation wrapped by the KMS, and how realtime recovers after the access token expires.", width: 1200, height: 780 }}>

### Chat encryption and realtime

Each chat message is encrypted with AES-256-GCM, using a random IV and salt per message. Every conversation has its own data key, stored wrapped by a KMS (AWS KMS or a local key, chosen by configuration) and kept in memory for five minutes, so the KMS is only called on a cache miss. The database stores the ciphertext, IV, auth tag and salt, never the plain text.

Realtime had a documented incident. Cloud Run's default request timeout of 300 seconds cut every WebSocket every five minutes, and a client that reconnected with an expired 15-minute token was disconnected by the gateway and never retried. The fix has two sides: the gateway now checks the token in a handshake middleware and rejects with a stable reason, and the client refreshes the token before each handshake and retries by itself with a capped backoff. The Cloud Run service settings are documented in the repo and changed by hand, not by the deploy workflow.

</DiagramRow>

### Sessions, audit and secrets

Sessions are short-lived: a 15-minute access token and a refresh token that rotates on every refresh. Presenting a refresh token that was already used revokes the whole session family, and roles are enforced through a decorator and a guard.

Audit logging is mandatory, and a single log table receives a record from every mutating or security-sensitive flow. Each row has the actor, the role at that moment, the condominium, a semantic event type and the context, and there are no anonymous logs. Revealing personal data, such as a visitor's document, is audited too. Secrets are scanned in four layers: a history audit, a pre-commit hook, a pre-push hook and a CI job.

### Visitors and access

A resident shares a link tied to their unit, valid for 24 hours. The visitor fills in a web form with no install, and the link is consumed. At the gate, a visitor who comes alone with a valid pass is checked in and the resident is only notified. A visitor with companions, or one with no pre-registration, needs approval: the resident gets a request, and whoever decides first, the resident or the guard, closes it.

</DiagramRow>

<DiagramRow item={{ src: "/diagrams/nido/order-lifecycle.svg", title: "Order life cycle", caption: "The states of a provider order, from the resident's request to a completed or closed order.", width: 1600, height: 680 }}>

### Marketplace orders

Orders to local providers follow a fixed set of states. The provider accepts or rejects, the resident can cancel until two hours before the slot, and payment is on delivery, confirmed by the provider. A payment problem closes the order with an incident.

</DiagramRow>

### Web, staff and mobile

Three clients share one API. The resident app is an Expo app with five tabs, and its Explore tab shows only the modules that the condominium has enabled. The staff app is a second Expo app for guards, with the same sign-in flow but a `STAFF` client flag that rejects residents. It lists visitors, shows the access history and verifies pass QR codes with the camera. The web portal is a static Next.js export with one area per role: condominium admin, platform admin, partner, provider and guard when the condominium allows it. A few public pages, such as visitor pre-registration and password setup, open from a link with no account.

</DiagramRow>

### Delivery

The API runs on Cloud Run with development, staging and production services, deployed by git tags. The web portal goes to Firebase Hosting and the two mobile apps are built and submitted with EAS, each with its own tag pattern. Every push or pull request to main runs dependency install, Prisma validation, linting, API and web tests with coverage, and SonarQube, Trivy and gitleaks scans.

### Working with AI agents

The repository includes a small harness for sessions of people and AI agents on one checkout: a registry of sessions with path claims, locks for shared resources, a leader agent that splits work, implementer and reviewer agents that write reports to disk, and written end-state criteria. People own git, and agents never commit.

### Decisions

These are the choices that shaped the platform, with the reason for each and what it cost.

| Decision | Why | Trade-off |
|---|---|---|
| Hexagonal modules with ports outside the shared types package | Keeps the domain free of frameworks and the shared package thin. | More files per module. |
| PostgreSQL plus MongoDB | Relational data for the platform and a document store for chat. | Two databases to run and back up. |
| Envelope encryption for chat | Messages stay private even from someone with database access. | Key management and a backfill for older data. |
| A single audit log table | One place to answer who did what. | Every mutation must remember to write to it. |
| A static web export | Cheap, fast hosting with no server to run. | No server-side rendering for the portal. |
| Receipt-based payments first | Fees can be collected now while the gateway is integrated gradually. | An admin validates receipts by hand. |
| Tolerant CSV import | Header matching ignores case, spaces, hyphens and dots, and accepts synonyms. | Looser validation on import files. |

<ResultsSection title="Results">

The client received a complete condominium platform: a web portal for administrators, guards, partners and providers, a resident app and a staff app, in Spanish and English with light and dark themes. Administrators can publish notices and manage the community from one place, residents authorize visitors, reserve common areas, join events, chat with neighbors and buy from local providers, and guards handle access from their own app. Partners and providers get their own space to offer benefits and products to the community.

One part is still being finished. The payment gateway is only partly integrated: fees are handled through a receipt-based flow, and the full online gateway flow is pending. No usage or satisfaction figures are reported yet.

</ResultsSection>
