<SummarySection title="Summary">

NIDO is a condominium management platform. A resident gets notices from the administration, authorizes visitors, reserves common areas, signs up for events, chats with neighbors, pays fees, buys from local providers and uses partner benefits.

It is a work project, not a personal one: it was built at Tres Astronautas for a client. The platform has an API, a web portal, a resident mobile app and a staff app, in Spanish and English with light and dark themes.

There are six roles: resident, guard, condominium admin, platform admin, partner and provider. The mobile app is for residents only, and every other role works from the web portal.

</SummarySection>

<ChallengeSection title="Challenge & strategy">

### Challenge

Life in a condominium ran through a lot of separate channels: group chats, paper notices, guard logbooks, receipts sent as screenshots and word of mouth for local services. Residents, administrators and guards each lost time to it, and local providers and partners had no clear way to reach the people living there.

### Strategy

The proposal was to bring those flows into one product, with the right tool for each role. That meant one app for daily life in a condominium, from notices and visitors to fees and local commerce, with a resident-only mobile app and a web portal for administration, guards, partners and providers. Many condominiums would share one platform, with data scoped to each of them.

Two principles shaped the design. Conversations had to be private, so chat messages are encrypted individually, with keys managed outside the database. And every sensitive action had to be traceable, so each mutating flow writes an audit record. Receipt-based payments came first, so fees could be collected right away while the payment gateway is integrated gradually.

</ChallengeSection>

<ImplementationSection title="Implementation & final design">

### Architecture

The repository is a monorepo with yarn workspaces and Turborepo: the API, the web portal, the resident app, the staff app and two shared packages, one for contracts and one for a profanity filter. Each API module is hexagonal, with a domain layer free of frameworks, an application layer with handlers, use cases and services, and an infrastructure layer with controllers and repositories. Dependencies only point inwards, and the rules are written down for people and for AI agents.

Data lives in two databases. PostgreSQL through Prisma holds the relational data, and MongoDB holds chat conversations, messages and read state. A Socket.IO gateway for chat runs in the same service as the REST API. The Next.js web portal is exported as static files, uses a locale segment in its routes and is served from Firebase Hosting.

### Security and privacy

Each chat message is encrypted with AES-256-GCM, using envelope encryption with a key from a KMS provider that is chosen by configuration. Sessions are short-lived: a 15-minute access token and a refresh token that rotates only when it is close to expiry, with roles enforced through a decorator and a guard.

Audit logging is mandatory, and a single log table receives a record from every mutating or security-sensitive flow. Secrets are scanned in four layers: a history audit, a pre-commit hook, a pre-push hook and a CI job.

### Delivery

The API runs on Cloud Run with development, staging and production services, deployed by git tags. Every push runs dependency install, Prisma validation, linting, API and web tests with coverage, and SonarQube and Trivy scans.

One real incident was documented. Cloud Run's default timeout cut the WebSocket connection every five minutes, and with a 15-minute token the chat died. The fix was a gateway check that rejects with stable reasons, plus token refresh with backoff in the client.

### Working with AI agents

The repository includes a small harness for sessions of people and AI agents on one checkout: a registry of sessions with path claims, locks for shared resources, a leader agent that splits work, implementer and reviewer agents that write reports to disk, and written end-state criteria. People own git, and agents never commit.

### Decisions

These are the choices that shaped the platform, with the reason for each and what it cost.

| Decision | Why | Trade-off |
|---|---|---|
| Hexagonal modules with ports outside the shared types package | Keeps the domain free of frameworks and the shared package thin. | More files per module. |
| PostgreSQL plus MongoDB | Relational data for the platform and a document store for chat. | Two databases to run and back up. |
| Envelope encryption for chat | Messages stay private even from someone with database access. | Key management and a backfill for older data. |
| A single audit log table | One place to answer who did what. | Every mutation must remember to write to it. |
| A static web export | Cheap, fast hosting with no server to run. | No server-side rendering for the portal. |
| Receipt-based payments first | Fees can be collected now while the gateway is integrated gradually. | An admin validates receipts by hand. |
| Permissive CSV import | Header matching ignores case and separators, and unknown headers are hints rather than errors. | Looser validation on import files. |

</ImplementationSection>

<ResultsSection title="Results">

The client received a complete condominium platform: a web portal for administrators, guards, partners and providers, a resident app and a staff app, in Spanish and English with light and dark themes. Administrators can publish notices and manage the community from one place, residents authorize visitors, reserve common areas, join events, chat with neighbors and buy from local providers, and guards handle access from their own app. Partners and providers get their own space to offer benefits and products to the community.

One part is still being finished. The payment gateway is only partly integrated: fees are handled through a receipt-based flow, and the full online gateway flow is pending. No usage or satisfaction figures are reported yet.

</ResultsSection>
