<SummarySection title="Resumen" nav="Resumen">

Telemetrix recibe lecturas de dispositivos por HTTP, WebSocket y MQTT, las guarda como series de tiempo, las muestra en gráficas y dashboards en tiempo real, y permite reaccionar a ellas con reglas, acciones salientes, tareas programadas, comandos a dispositivos y análisis en un entorno aislado.

Los datos se organizan en canales: un canal agrupa hasta ocho campos de datos, además de ubicación y estado. Es un producto propio, diseñado desde cero para makers y para equipos que lo integran en sus propios sistemas.

</SummarySection>

<ChallengeSection title="Reto y estrategia" nav="Reto">

### Reto

Empezó con un vacío. De un lado están las herramientas para aficionados, buenas para un prototipo de fin de semana; del otro, las plataformas industriales hechas para empresas con un equipo que las opere. Los makers y los equipos pequeños quedan en medio: necesitan recoger datos de sus dispositivos, verlos en vivo y reaccionar a ellos, pero no quieren armar y operar un stack de brokers, bases de datos y dashboards solo para lograrlo.

El modelo de negocio hizo el problema más difícil. Telemetrix se planeó como un SaaS con un plan gratuito masivo para makers, y clientes de pago que integran la plataforma en sus propios sistemas. Con cerca del 80% de los dispositivos esperados en el plan Free, cada dispositivo gratuito tenía que costar casi nada de servir, así que el diseño no podía permitirse desperdicio en la ruta crítica.

### Estrategia

El plan partió del dispositivo. Un dispositivo solo debería necesitar una API key y sus identificadores para empezar a enviar lecturas, ya sea por HTTP, MQTT o WebSocket. A partir de ahí, la decisión más importante fue mantener la ingesta independiente de la base de datos: una lectura se confirma cuando está segura en el buffer de eventos, no cuando llega al almacenamiento de series de tiempo, con una meta de diseño de confirmación p99 de 50 ms o menos. Luego una lectura debe llegar al dashboard en menos de 2 segundos (p95), para que las personas vean lo que hacen sus dispositivos en el momento en que pasa.

El costo y la seguridad definieron el resto. Los límites de cada plan se aplican en el borde, antes de tocar cualquier recurso costoso, lo que mantiene sostenible el plan gratuito. Los canales son privados al crearse, las API keys se guardan solo como un HMAC, TLS es un requisito en producción y cada recurso está aislado por su dueño. Todo esto se dimensionó para 100.000 dispositivos activos en el primer año, un supuesto de planeación, con margen para 250.000 conexiones MQTT simultáneas.

</ChallengeSection>

<FeaturesSection title="Funcionalidades" nav="Funcionalidades">

La documentación del backlog define 16 capacidades y 85 funcionalidades. Las principales:

| Capacidad | Qué permite |
|---|---|
| Identidad y acceso | Registro e inicio de sesión con contraseña, roles globales (owner y developer), tokens personales de API y cierre de las sesiones activas. |
| Dispositivos y credenciales | Registrar dispositivos, generar una API key por cuenta con tres encabezados por dispositivo, y ver el último contacto y el estado de conexión. |
| Ingesta | Lecturas individuales y por lote por HTTP, publicación por MQTT y WebSocket, validación y normalización del payload, idempotencia por mensaje y límites de tasa según el plan. |
| Canales y datos | Crear canales de hasta ocho campos, editarlos, consultar feeds con filtros y agregaciones por intervalo, exportar a CSV, JSON o XML, e importar historial desde CSV. |
| Visualización | Gráficas en tiempo real por campo, indicadores, medidores y lámparas, dashboards con varios canales, un mapa de ubicación y canales públicos embebibles. |
| Móvil | Inicio de sesión, navegación por canales y dashboards, datos en tiempo real y notificaciones push. |
| Reglas y acciones | Umbrales y condiciones compuestas, detección de datos faltantes, tiempo de espera entre disparos, y acciones salientes: webhooks, correo, SMS, push y solicitudes HTTP. |
| Programación y análisis | Tareas únicas o recurrentes con zonas horarias, y scripts de análisis en un entorno aislado que escriben resultados en canales derivados. |
| Comandos | Colas de comandos hacia los dispositivos por HTTP y MQTT, con confirmación de ejecución. |
| Operación y auditoría | Registro de auditoría inmutable, una consola de owner con lecturas auditadas, un dashboard de salud y trazas de extremo a extremo. |

### Decisiones

| Decisión | Por qué | Qué cambió frente al plan 1.0 |
|---|---|---|
| Monolito modular en lugar de servicios separados | El equipo es pequeño, y dividir por dominio multiplica la operación y la consistencia distribuida sin beneficio. La separación se mantuvo solo donde el perfil de carga es distinto, y esos casos viven como módulos del mismo proceso. | De siete servicios por perfil de carga (ADR-002) a un monolito modular (ADR-021). |
| Supabase Postgres en lugar de RDS | Un servicio administrado reduce la operación de la base de datos. | Reemplaza RDS (ADR-018). |
| Postgres particionado sin TimescaleDB | Supabase dejó de ofrecer la extensión en Postgres 17. | Se pierde la compresión columnar de cerca de diez veces. Con la carga nominal, el volumen bruto pasa de unos 1,3 TB a unos 13 TB por mes (ADR-019). |
| Supabase Auth en lugar de Keycloak | Evita operar un proveedor de identidad propio, y ya está integrado con la base de datos. | Reemplaza Keycloak (ADR-020). |
| Redis Streams en lugar de NATS JetStream | Redis ya estaba en el stack para caché, así que evita otra pieza de infraestructura. | Reemplaza NATS (ADR-022). Menor durabilidad y capacidad de buffer que JetStream replicado. |
| Roles globales sin organizaciones | El aislamiento de recursos por dueño basta para el caso de uso real y simplifica permisos y facturación. | Elimina el modelo multiorganización de la versión 1.0 (ADR-023). |
| API key por cuenta con HMAC, sin Argon2 | Con 256 bits de entropía un hash lento es innecesario, y pesaría sobre la ruta crítica de ingesta. | Decisión nueva para dispositivos (ADR-025). |
| MQTT también para las apps | El producto debe soportar los tres transportes de extremo a extremo. Los comandos siguen pasando por la API para validar, auditar y entregar. | Excepción a ADR-012, que daba MQTT solo a los dispositivos (ADR-025). |
| Sin APISIX, Terraform ni AWS | El producto se simplificó y solo existe el entorno local, así que no vale la pena elegir un proveedor antes de tener datos reales de carga y costo. | Reemplaza el plan de AWS y EKS (ADR-030). Todavía no hay camino a producción: ni Dockerfile de la API, ni CI, ni borde TLS, ni observabilidad. |
| Escrituras por lotes y caché de lectura | El cuello de botella era Postgres, con muchos lectores de dashboards y muchos dispositivos escribiendo. | Decisión nueva de carga (ADR-029). |

Dos cosas se documentaron como evolución, no como errores. La versión 1.0 menciona Go 1.23, Next.js 15 y Expo SDK 52, mientras que el README actual indica Go 1.26, Next.js 16 y Expo SDK 57. ADR-024 (un código de un solo uso por dispositivo) fue reemplazada: el inicio de sesión es solo con contraseña.

<ResultsSection title="Resultados" nav="Resultados">

Para un maker o un equipo pequeño, el resultado es una plataforma que ya cubre el camino del dispositivo a la decisión. Los dispositivos envían lecturas por HTTP, MQTT o WebSocket y las ven en dashboards en vivo, y las personas pueden reaccionar a ellas con reglas, acciones salientes, tareas programadas, comandos a dispositivos y análisis en un entorno aislado, desde una consola web y una app móvil. Una lectura está diseñada para llegar al dashboard en menos de 2 segundos.

El producto sigue en desarrollo, y no todas las 85 funcionalidades del backlog están verificadas como completas. Algunas piezas pendientes son TLS en producción, terminar la retención de telemetría y permitir que los espacios compartidos envíen valores a los dispositivos. Las metas de rendimiento son objetivos de diseño, no resultados medidos.

</ResultsSection>
