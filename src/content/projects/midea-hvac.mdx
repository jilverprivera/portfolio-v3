<SummarySection title="Summary">

This is an ecosystem platform for Midea Germany's HVAC business. It brings installers, technicians, trainers and sales people into one portal, and gives Midea's team a back-office to manage everything they see.

It is a work project, not a personal one: it was built at Tres Astronautas for a client. The monorepo contains a user portal, an admin back-office and the REST API behind both, in German and English.

The portal's most distinctive tool is a thermal load calculator that sizes air-conditioning equipment for a building, room by room.

</SummarySection>

<ChallengeSection title="Challenge & strategy">

### Challenge

Midea's HVAC business depends on a network of installers, technicians and trainers who need current product information, manuals, training and a way to size equipment correctly. Doing that across emails, PDFs and spreadsheets was slow and hard to keep consistent.

### Strategy

The proposal was to put it all in one place: a portal where installers, technicians, trainers and sales people share products, documentation, training and commissioning. People would arrive with the Midea account they already have through single sign-on and be provisioned automatically, with the language and permissions that each audience needs.

Several decisions followed from that. Permissions are stored in the database and edited from the admin, so roles can change without a deploy. The platform is bilingual by design: German is the default locale, English is available everywhere, and domain content is stored in both languages. And every business action leaves a record of who did what and whether it succeeded.

</ChallengeSection>

<FeaturesSection title="Features">

| Area | What it enables |
|---|---|
| Authentication | Email and password with a one-time code, assisted registration by an admin, public self-registration, password reset, forced password change on first login and rotating refresh tokens. |
| Single sign-on | OAuth 2.0 against Midea's identity provider, with automatic user provisioning and a role-selection step for new users. |
| Roles and permissions | Roles mapped to modules and to actions (view, create, edit, delete, use, download), enforced on the server for each request. |
| Product catalog | A taxonomy of categories, subcategories, series and tiers, with product sheets, compatibilities, combinations, 3D models and multimedia, plus a guided create and edit wizard. |
| Documentation center | Manuals and resources with versions, independent publishing per resource and per version, and assignment to several products. |
| Thermal calculator | Room-by-room load estimation, indoor and outdoor unit suggestions, multi-split combinations, saved and shareable results, and a PDF export. |
| Training and roadshows | Events with participants, trainer statistics and certificates, with scheduled jobs that start and close events automatically. |
| Commissioning | Installers request a commissioning, a commissioner accepts, performs and certifies it with photo evidence. |
| Admin settings | A landing carousel, social links and legal documents such as terms, privacy and the imprint. |
| Audit log | An event log with status, priority and actor, and an admin screen with dashboard statistics. |

### The thermal calculator

The calculation estimates the load of each room from its volume and from the people in it, then adds the rooms together. It then compares that load with the nominal capacity of each candidate indoor unit and classifies the match as undersized, optimal or acceptable. For multi-split systems it picks the smallest outdoor unit that covers the load and has a valid combination, and spreads the load over several outdoor units when one is not enough. The method is documented with worked examples in the repository.

<ImplementationSection title="Implementation & final design">

### Architecture

The repository is a monorepo with yarn workspaces and Turborepo: three apps (the API, the portal and the admin) and two shared packages, one with TypeScript contracts and one with the design system. Each API feature is a hexagonal module, with a domain layer that never imports Nest.js or Prisma, an application layer with handlers and use cases, and an infrastructure layer with controllers and repositories. Modules talk to each other only through exported handlers or ports.

The types package mirrors the database enums and the JSON shapes, so the frontends never depend on the Prisma client. The portal and the admin share one UI package built with Atomic Design, shadcn components, rich text and data tables.

### Authorization and security

Permissions are decided on the server by a global guard that checks the role's module and action, using data stored in the database. The frontends only read permissions to hide what a user cannot use. The API also uses Helmet, throttling, an HTML sanitization pipe and strict validation that rejects unknown fields, and raw SQL is blocked by default in the database service. Secrets are scanned with gitleaks as a pre-commit hook, plus Trivy and SonarQube in CI.

### Files, language and delivery

Large files go directly to Google Cloud Storage with signed URLs, in resumable chunks, so they never pass through the API. When only one language is supplied for a piece of content, the API fills the other with Google Cloud Translation.

Deployments are driven by tags: a tag names the app and the environment, and the pipeline builds a Docker image, pushes it and deploys to Cloud Run, with the two frontends behind Firebase Hosting. Work is spec-driven, so features start as written specs, and the repository carries rules and skills for AI coding agents.

### Decisions

These are the choices that shaped the platform, with the reason for each and what it cost.

| Decision | Why | Trade-off |
|---|---|---|
| Hexagonal modules per feature | Keeps the domain free of frameworks and easy to test. | More boilerplate, and very large repositories in the products module. |
| Permissions stored in the database | Roles can be edited at runtime without a deploy. | One extra query on every guarded request. |
| A shared types package | One source of truth for contracts across three apps. | It has to be built before the apps that use it. |
| Separate portal and admin | Different audiences and navigation, one design system. | Two Next.js apps to deploy and maintain. |
| Direct-to-storage uploads | Large manuals and media should not load the API. | The upload flow lives in the client. |
| Bilingual content as data | Every piece of domain content exists in German and English. | Editors work with two fields, and automatic translation fills gaps. |

</ImplementationSection>

<ResultsSection title="Results">

The client received one portal that brings installers, technicians, trainers and sales people together, and a back-office where the team manages everything they see. Professionals can browse the product catalog, find documentation in one place, follow training and roadshows, and take part in commissioning. The thermal load calculator lets them size air-conditioning equipment for a building room by room, and the administrators manage users, roles and content, and can review the audit log.

Some parts are still evolving. The calculator is a simplified model for now, and some pages show placeholder data, such as roadshow statistics. No adoption figures are reported yet.

</ResultsSection>
